RENCANA PERBAIKAN AETHERMASTER-AI
================================

Scope proyek:
Aplikasi saat ini digunakan untuk pengembangan dan pengujian lokal. Fokus perbaikan adalah correctness, konsistensi game state, stabilitas AI narrative, database consistency, dan kualitas gameplay. Security hardening, authentication, session ownership, CORS restriction, dan production deployment bukan prioritas pada fase ini.

Tujuan utama:
Memperbaiki AetherMaster-AI agar game state konsisten, aman, dapat di-rewind dengan benar, tidak terlalu bergantung pada keputusan Gemini, dan memiliki alur narrative engine yang stabil tanpa menghilangkan fitur yang sudah berjalan.

PRINSIP ARSITEKTUR
------------------
1. Gemini berperan sebagai AI narrative/intent layer, bukan sumber kebenaran game state.
2. Backend/Game Engine menjadi satu-satunya sumber kebenaran untuk HP, mana, gold, inventory, quest, reputation, combat, dan kondisi game over.
3. Frontend hanya mengirim aksi dan merender state yang diberikan backend.
4. Semua perubahan state penting harus tervalidasi sebelum disimpan.
5. StoryNode harus mampu merepresentasikan state yang diperlukan untuk rewind.
6. Jangan menghapus fitur yang sudah ada kecuali memang diperlukan untuk memperbaiki bug.
7. Jangan mengubah UI secara besar-besaran jika tidak diperlukan untuk perbaikan backend.
8. Jangan menambahkan fitur AI baru sebelum state engine stabil.

FASE 3 - PERBAIKAN REWIND
==================================================

BUG:
Rewind saat ini mengembalikan sebagian character state tetapi tidak sepenuhnya mengembalikan world state.

Perbaiki agar setiap StoryNode yang diperlukan memiliki snapshot state lengkap.

Minimal snapshot:
- hp
- maxHp
- mana
- maxMana
- gold
- inventory
- equippedItems
- statusEffects
- worldLedger
- missionLog
- combatState
- turnCount
- isGameOver

Jika diperlukan, gunakan:
gameStateSnapshot: {...}

Saat rewind:
1. Validasi target node milik session.
2. Ambil snapshot target.
3. Restore seluruh state dari snapshot.
4. Jangan otomatis menghidupkan karakter jika snapshot menunjukkan HP <= 0.
5. Jangan mengubah HP menjadi 50% hanya karena rewind.
6. Restore worldLedger.
7. Restore missionLog.
8. Restore combatState.
9. Restore isGameOver sesuai state target.
10. Simpan seluruh state secara atomik.

Jika target node tidak memiliki snapshot lengkap karena save lama, buat fallback yang aman dan dokumentasikan keterbatasannya.

==================================================
FASE 4 - COMBAT VALIDATION
==================================================

BUG:
Endpoint combat berpotensi membuat combat baru walaupun current scene tidak memiliki combat encounter.

Aturan baru:
- combat hanya boleh dimulai jika currentNode memiliki combatEncounter valid.
- Jika tidak ada encounter, return HTTP 400.
- Jangan membuat enemy default secara diam-diam.
- Validasi bahwa combatState memang berasal dari encounter yang sedang aktif.
- Validasi setiap combat action di backend.
- Jangan percaya HP yang dikirim frontend.
- Jangan percaya damage/result yang dikirim frontend.
- Semua HP perubahan dihitung backend.
- Setelah combat selesai, simpan state secara atomik.

Combat state harus memiliki struktur yang jelas, misalnya:
- active
- encounterId
- enemyId
- enemyHp
- playerTurn
- turnCount
- status

Sesuaikan dengan implementasi combat aktual repository.

==================================================
FASE 6 - STRICT DATA SCHEMA
==================================================

Perketat semua schema Zod yang saat ini menggunakan z.any() atau tipe terlalu longgar.

Minimal:
- scene
- choice
- stateUpdates
- item
- combatEncounter
- missionLog
- reputation
- worldLedger

Pastikan field yang memang digunakan backend juga ada di schema.

Contoh masalah yang harus dicek:
Backend membaca:
stateUpdates.reputation

Tetapi schema harus benar-benar mendefinisikan:
reputation

Jangan memiliki field yang:
- diharapkan backend
- dikirim AI
- tetapi dibuang parser/schema.

==================================================
FASE 7 - ITEM SYSTEM
==================================================

Hilangkan ketergantungan berlebihan terhadap string matching seperti:
item.id.includes('potion')
item.id.includes('elixir')
item.name.includes(...)

Gunakan struktur item yang eksplisit.

Contoh:
{
  id: "item_001",
  name: "Potion of Healing",
  type: "consumable",
  category: "medicine",
  effects: {
    hp: 25,
    mana: 0
  }
}

Backend menentukan efek berdasarkan data item, bukan berdasarkan nama item.

Buat item master data/constants jika sesuai dengan arsitektur repository.

Pastikan ID item konsisten di seluruh:
- backend
- frontend
- seed
- campaign
- fallback
- database
- save/import/export

==================================================
FASE 8 - QUEST DAN MISSION STATE
==================================================

Jangan gunakan turnCount sebagai sumber utama penentuan ending.

TurnCount hanya untuk:
- pacing
- statistik
- informasi UI

Ending harus berdasarkan state objektif.

Contoh:
- quest completed
- required objective completed
- final encounter resolved
- player defeated
- explicit valid ending condition

Buat struktur quest state yang jelas.

MissionLog harus benar-benar dipersist jika berubah.

Saat scene baru menghasilkan perubahan objective:
- validate
- update mission state
- save
- gunakan state tersebut untuk narrative berikutnya.

==================================================
FASE 9 - WORLD LEDGER
==================================================

World ledger harus menyimpan structured facts, bukan hanya string dengan key seperti:
turn_5

Gunakan struktur event/fact yang dapat dilacak.

Contoh:
{
  facts: [
    {
      id: "fact_001",
      type: "NPC_HELPED",
      target: "elder_01",
      turn: 4
    }
  ],
  questFlags: {},
  reputation: {}
}

Pastikan:
- duplicate fact dapat dikendalikan.
- fact dapat di-query.
- rewind dapat mengembalikan ledger.
- save/load mempertahankan ledger.
- AI menerima informasi ledger yang relevan.

==================================================
FASE 10 - GEMINI OUTPUT DAN PARSING
==================================================

Gunakan structured output dari Gemini SDK jika fitur/model yang digunakan mendukungnya.

Jangan menjadikan regex:
rawText.match(/\{[\s\S]*\}/)

sebagai parser JSON utama.

Flow:
Gemini structured output
    ->
schema validation
    ->
state/event validation
    ->
game engine
    ->
narrative scene

Jika structured output gagal:
1. retry terbatas.
2. repair terkontrol jika diperlukan.
3. deterministic fallback.

Jangan melakukan retry tanpa batas.

==================================================
FASE 11 - FALLBACK
==================================================

Fallback harus:
- generic
- state-aware
- campaign-aware
- tidak memberikan reward arbitrer
- tidak mengubah HP tanpa alasan yang tervalidasi
- tidak memaksa ending hanya karena jumlah turn
- tidak terlalu bergantung pada keyword tertentu

Hindari sistem seperti:
jika teks mengandung "pedang" -> branch A
jika mengandung "lari" -> branch B

Gunakan intent classification atau rule yang lebih terstruktur.

Fallback harus menghasilkan scene valid sesuai schema.

==================================================
FASE 12 - RETRY DAN ERROR HANDLING GEMINI
==================================================

Bedakan:
- authentication error
- invalid request
- rate limit
- timeout
- server error
- schema validation error

Jangan selalu mencoba banyak model tanpa alasan.

Pastikan retry:
- memiliki batas.
- memiliki timeout.
- tidak menghasilkan request berlebihan.
- tidak membuat player menunggu terlalu lama.

Jangan pernah memasukkan API key ke log.

==================================================
FASE 13 - DATABASE TRANSACTION
==================================================

Operasi yang mengubah banyak record harus menggunakan transaction jika memungkinkan.

Minimal audit:
- submitAction
- advanceStoryState
- combatAction
- saveToSlot
- loadFromSlot
- rewind
- importSessionJson

Jika salah satu langkah gagal:
- rollback perubahan.

Jangan meninggalkan:
- character baru tanpa session
- session tanpa node
- save slot setengah terbuat
- node tanpa hubungan parent yang benar

==================================================
FASE 14 - SAVE/LOAD
==================================================

Perbaiki save cloning agar:
- seluruh state konsisten.
- currentSceneId benar.
- parentNodeId benar.
- character snapshot benar.
- worldLedger benar.
- missionLog benar.
- combatState benar.

Gunakan pola dua tahap:
1. clone semua node.
2. map parentNodeId.

Gunakan transaction.

Pastikan penghapusan save lama tidak meninggalkan orphan record.
