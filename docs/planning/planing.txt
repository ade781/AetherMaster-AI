============================================================
TUJUAN REFACTOR
===============

Lakukan audit dan refactor menyeluruh terhadap AetherMaster dengan fokus pada:

* konsistensi database
* single source of truth
* Game State Engine
* Item
* NPC
* Location
* Quest
* Quest Objective
* World Fact
* Story Node
* Story Choice
* Story Snapshot
* branching timeline
* rewind
* save/load
* journal
* inventory
* Gemini integration
* fallback system
* validasi AI output
* frontend state consistency
* integration testing

PRINSIP UTAMA:

Database menjadi sumber data dunia.

GameStateEngine menjadi sumber kebenaran game state.

QuestEngine menjadi sumber kebenaran progression Quest.

WorldFact menjadi sumber history dunia.

StorySnapshot menjadi sumber restore state.

Gemini menjadi narrative engine, bukan game-state authority.

Frontend hanya merender state dari backend.

COMBAT TIDAK TERMASUK DALAM REFACTOR INI.

============================================================
HASIL AUDIT
===========

1. ITEM DATABASE DAN ITEM MASTER MASIH MENJADI DUA SUMBER DATA

---

Saat ini masih terdapat beberapa sumber definisi Item:

* database Item
* ItemRepository
* itemMaster.js
* ITEM_CATALOG
* DEFAULT_ITEM_CATALOG
* resolver Item legacy

GameStateEngine masih bergantung pada itemMaster.

Masalah:

* database Item belum benar-benar menjadi single source of truth
* perubahan Item di database belum tentu memengaruhi seluruh gameplay
* definisi Item dapat berbeda antar sistem
* ID Item dapat tidak konsisten
* sistem lama dan sistem database berjalan bersamaan

TARGET:

Database Item harus menjadi satu-satunya sumber definisi Item.

Arsitektur:

Item Database
->
ItemRepository
->
GameStateEngine
->
Game State

2. AI MASIH DAPAT MEMBUAT ITEM YANG TIDAK ADA DI DATABASE

---

addItem() masih dapat menerima object Item secara langsung jika lookup gagal.

Opening scene juga masih dapat memasukkan receivedItem dari output AI ke inventory.

Masalah:

Gemini secara tidak langsung masih dapat membuat Item baru yang tidak terdaftar di database.

TARGET:

Gemini hanya boleh memberikan ID.

Contoh:

receivedItemId = "item_potion_small"

Backend kemudian:

receivedItemId
->
ItemRepository
->
validasi Item
->
GameStateEngine
->
Inventory

Jika Item tidak ditemukan di database, Item harus ditolak.

3. finish_game MASIH DAPAT MEMBYPASS GAME LOGIC

---

Masih terdapat jalur:

choiceId = "finish_game"
->
session.isGameOver = true

Masalah:

Ending dapat dipicu tanpa memastikan objective Quest atau kondisi campaign terpenuhi.

TARGET:

Player Action
->
Game Event
->
Quest Engine
->
Objective Validation
->
Ending Validation
->
Game Over

Jika campaign memang mengizinkan ending langsung, tetap harus ada kondisi backend yang memvalidasinya.

4. QUEST MASIH MEMILIKI MULTIPLE SOURCE OF TRUTH

---

Quest saat ini tersebar pada:

* Quest database
* QuestObjective database
* CAMPAIGN_OBJECTIVES
* missionLog
* worldLedger
* state tertentu

Masalah:

Beberapa sistem dapat memiliki status Quest yang berbeda.

TARGET:

Gunakan:

Quest
->
QuestObjective
->
QuestEngine
->
Session Runtime Progress

CAMPAIGN_OBJECTIVES harus dihapus setelah seluruh data dimigrasikan ke database.

5. AI MASIH DAPAT MEMPENGARUHI QUEST COMPLETION TERLALU LANGSUNG

---

questEngine masih membaca update missionLog dari AI.

Masalah:

AI dapat mengusulkan status objective.

Narrative AI seharusnya tidak menjadi pihak yang menentukan apakah sebuah Quest selesai.

TARGET:

Player Action
->
Game Event
->
QuestEngine
->
Objective Evaluation
->
Quest Progress

Gemini hanya boleh menghasilkan:

* narrative
* dialogue
* scene description
* proposed event

Backend yang menentukan apakah event tersebut valid dan mengubah state.

6. TERDAPAT DUA SISTEM SNAPSHOT

---

Saat ini terdapat:

* StoryNode.gameStateSnapshot
* StoryNode.characterSnapshot
* StorySnapshot table

Tetapi restore masih menggunakan snapshot yang tersimpan pada StoryNode.

Masalah:

* redundant data
* dua sumber snapshot
* perubahan pada StorySnapshot tidak otomatis digunakan oleh rewind
* potensi state mismatch

TARGET:

StorySnapshot menjadi satu-satunya sistem snapshot resmi.

Arsitektur:

StoryNode
->
StorySnapshot
->
GameStateEngine.restoreSnapshot()

7. WORLD LEDGER DAN WORLD FACT MASIH DUPLIKAT

---

Saat ini world state/history masih dapat disimpan melalui:

* GameSession.worldLedger
* WorldFact database

Masalah:

Satu fakta dapat berada di dua tempat.

Contoh:

Turn 1:
Fact A

Turn 2:
Fact B

Turn 3:
Fact C

Rewind ke Turn 1.

Session worldLedger dapat kembali ke:

Fact A

Tetapi WorldFact database masih dapat memiliki:

Fact A
Fact B
Fact C

Journal kemudian dapat menampilkan fakta dari masa depan.

TARGET:

WorldFact database menjadi sumber history dunia.

worldLedger hanya boleh menjadi derived context/cache jika benar-benar dibutuhkan.

8. REWIND BELUM MEMILIKI MODEL BRANCHING YANG TEGAS

---

StoryNode sudah berbentuk tree, tetapi sistem belum sepenuhnya menentukan bagaimana future state diperlakukan setelah rewind.

Ada dua kemungkinan:

A. Future node dihapus.

B. Future node menjadi abandoned branch.

Gunakan pendekatan B.

Contoh:

A -> B -> C -> D

Rewind ke B.

Kemudian player melakukan pilihan baru:

A -> B -> E -> F

Branch C-D menjadi:

ABANDONED

TARGET:

Tambahkan konsep:

* branchId
* activeBranchId
* branch status
* currentNodeId
* parentNodeId

Status branch:

ACTIVE
ABANDONED

9. SAVE/LOAD BELUM MENANGANI SELURUH STORY GRAPH

---

Database memiliki:

* StoryNode
* StoryChoice
* StorySnapshot
* WorldFact

Tetapi save/load harus memastikan seluruh graph ikut disimpan dan dipulihkan.

Masalah jika hanya StoryNode yang dicloning:

* StoryChoice dapat hilang
* StorySnapshot dapat hilang
* WorldFact dapat tidak ikut
* parent-child relationship dapat rusak
* branch relationship dapat hilang

TARGET:

Save harus mencakup:

Session
Character
StoryNode
StoryChoice
StorySnapshot
WorldFact
Branch
ActiveBranch
CurrentNode

Seluruh operasi save/load harus dilakukan secara transactional.

10. STORYCHOICE MASIH MEMILIKI DOUBLE STORAGE

---

StoryNode masih memiliki choices dalam JSON.

Di sisi lain terdapat tabel StoryChoice.

Frontend masih menggunakan node.choices.

Masalah:

Dua sistem dapat memiliki data berbeda.

TARGET:

Flow:

->

->

->
Frontend

Jika node.choices tetap dipertahankan untuk compatibility sementara, jangan izinkan dua sistem melakukan write.

* nearbyNpcs

TARGET:

=================

## PHASE 1 - CANONICAL DATA MODEL

Buat dokumentasi:

* source of truth

## PHASE 2 - ITEM SINGLE SOURCE OF TRUTH

1. Pastikan seluruh Item berada di database.
2. Pastikan ItemRepository lengkap.
3. Ubah GameStateEngine agar mengambil Item dari repository.
4. Ubah inventory menjadi itemId + quantity.
5. Jangan menyimpan metadata Item sebagai state permanen.
6. Hapus ITEM_CATALOG.
7. Hapus DEFAULT_ITEM_CATALOG.
8. Hapus resolver Item legacy.
9. Tambahkan validasi Item ID.
10. Test acquire.
11. Test use.
12. Test invalid Item.
13. Test quantity.
14. Test rewind.

## PHASE 3 - QUEST SINGLE SOURCE OF TRUTH

1. Migrasikan seluruh campaign objective ke QuestObjective.
2. Hapus CAMPAIGN_OBJECTIVES.
3. QuestEngine membaca QuestRepository.
4. QuestEngine membaca QuestObjectiveRepository.
5. Session hanya menyimpan runtime progress.
6. AI tidak boleh menentukan completion.
7. Objective selesai berdasarkan event/game condition.
8. Ending harus bergantung pada kondisi Quest/campaign yang valid.

## PHASE 4 - GAME EVENT SYSTEM

Gunakan event internal.

Contoh:

NPC_TALKED
ITEM_ACQUIRED
ITEM_USED
LOCATION_ENTERED
FACT_DISCOVERED
QUEST_OBJECTIVE_COMPLETED
COMBAT_VICTORY
COMBAT_FLED

Event digunakan sebagai input untuk:

* QuestEngine
* WorldFact
* Timeline
* Snapshot

COMBAT hanya boleh menjadi producer/consumer event jika diperlukan.

JANGAN mengubah mekanisme combat.

## PHASE 5 - SNAPSHOT REFACTOR

1. Jadikan StorySnapshot sebagai snapshot resmi.
2. Hapus redundant gameStateSnapshot.
3. Hapus redundant characterSnapshot jika tidak diperlukan.
4. Restore hanya melalui GameStateEngine.
5. Pastikan snapshot mencakup:

* character
* inventory
* quest state
* world state
* current location
* current story node
* active branch

## PHASE 6 - WORLD FACT REFACTOR

1. Jadikan WorldFact sebagai sumber world history.
2. Hindari penyimpanan fakta yang sama sebagai source of truth di worldLedger.
3. worldLedger hanya boleh menjadi derived/cache context jika memang dibutuhkan.
4. WorldFact harus terhubung dengan story node/branch.
5. Rewind harus menentukan WorldFact mana yang aktif.

## PHASE 7 - BRANCHING TIMELINE

* branchId

* activeBranchId

2. restore snapshot
3. buat branch baru
4. jadikan future branch sebagai abandoned

6. set currentNodeId
