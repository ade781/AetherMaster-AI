# 2. Buat schema data yang ketat

Cari seluruh penggunaan `z.any()` yang berkaitan dengan scene/state.

Khususnya:

```js
receivedItem: z.any()
consumedItem: z.any()
combatEncounter: z.any()
```

Ganti dengan schema terstruktur.

Buat schema item yang konsisten, misalnya:

```js
const itemSchema = z.object({
  id: z.string(),
  name: z.string(),
  category: z.string(),
  effect: z.string(),
  icon: z.string()
});
```

Sesuaikan dengan struktur database/model yang sebenarnya jika repository memiliki definisi item sendiri.

Jangan membuat schema yang bertentangan dengan database.

Pastikan:

* Scene tervalidasi
* Choice tervalidasi
* Item tervalidasi
* State update tervalidasi
* Mood tervalidasi
* Character ID tervalidasi bila memungkinkan
* Background ID tervalidasi bila memungkinkan

---

# 3. Perbaiki JSON generation

Saat ini parsing menggunakan:

```js
const match = rawText.match(/\{[\s\S]*\}/);
const parsed = JSON.parse(match ? match[0] : rawText);
```

Ini rapuh.

Cari kemampuan structured output/JSON schema yang sudah didukung oleh SDK Gemini yang digunakan project.

Gunakan structured output jika kompatibel dengan versi dependency yang terpasang.

Prioritas:

1. Gemini menghasilkan struktur JSON tervalidasi.
2. Zod melakukan validasi tambahan.
3. Jika output invalid, lakukan repair/retry terbatas.
4. Jika semua gagal, gunakan deterministic fallback.

Jangan mengandalkan regex `{...}` sebagai parser JSON utama.

Tetap sediakan fallback agar sistem tidak crash ketika Gemini gagal.

# 4. Perbaiki fallback narrative

Fallback saat ini terlalu bergantung pada keyword:

```js
if (lowerAction.includes('interogasi'))
else if (lowerAction.includes('periksa'))
else if (lowerAction.includes('serang'))
else if (lowerAction.includes('sihir'))
...
```

Jangan langsung menghapus fallback.

Refactor agar fallback menjadi lebih generik dan aman.

Fallback harus:

* tetap mempertahankan konteks lokasi
* mempertahankan karakter
* mempertahankan quest/world state
* tidak mengarang item secara sembarangan
* tidak mengarang reward tanpa validasi
* tidak otomatis menyatakan pemain berhasil
* tidak mengubah game state secara arbitrer

Jika diperlukan, buat fungsi:

```js
classifyPlayerIntent()
```

atau struktur intent sederhana yang dapat digunakan baik oleh AI maupun deterministic fallback.

Contoh intent:

```text
TALK
INVESTIGATE
MOVE
ATTACK
MAGIC
STEALTH
USE_ITEM
OBSERVE
INTERACT
UNKNOWN
```

Tetapi jangan membuat klasifikasi keyword yang terlalu kompleks jika intent sebenarnya dapat diperoleh dari model.

# 5. Game state harus deterministic

Buat atau refactor Game State Engine.

Minimal harus memiliki konsep:

```js
playerState
worldState
questState
inventory
reputation
history
```

Semua perubahan state harus melalui fungsi/service terpusat.

Contoh konsep:

```js
applyStateUpdate(state, event)
```

atau:

```js
gameEngine.resolveAction(state, action)
```

Jangan biarkan berbagai service langsung melakukan:

```js
character.hp += ...
character.gold += ...
```

secara tersebar.

Buat satu sumber kebenaran untuk mutasi state.

# 6. Jangan gunakan turnCount sebagai syarat kemenangan

Saat ini terdapat logic seperti:

```js
if (turnCount >= 11)
```

yang memaksa Grand Finale.

Hapus ketergantungan langsung antara jumlah turn dan kemenangan.

Turn count hanya boleh digunakan untuk pacing.

Ending harus bergantung pada kondisi dunia/quest, misalnya secara konseptual:

```js
mainQuestCompleted
finalEncounterCompleted
requiredObjectivesCompleted
```

Gunakan struktur quest yang memang sudah ada di repository jika tersedia.

Jika belum ada quest-state yang cukup kuat, buat perubahan minimal yang diperlukan.

Jangan membuat pemain menang hanya karena sudah memilih aksi sebanyak 12 kali.

# 7. World Ledger harus menyimpan fakta, bukan hanya narasi

Audit `worldLedger`.

Jika sekarang hanya menyimpan string seperti:

```js
addLedgerFact
```

perbaiki secara bertahap agar fakta penting dapat disimpan secara terstruktur.

Contoh:

```js
{
  type: "ITEM_ACQUIRED",
  itemId: "item_06_skeleton_key",
  turn: 4
}
```

atau struktur ekuivalen yang sesuai dengan repository.

World ledger harus dapat merepresentasikan fakta seperti:

* item diperoleh
* item digunakan
* pintu terbuka
* NPC sudah ditemui
* NPC memberikan informasi
* quest objective selesai
* lokasi telah dikunjungi
* faction reputation berubah
* event penting telah terjadi

Narasi dapat berubah.

Fakta dunia tidak boleh berubah hanya karena model lupa.

# 16. Testing

Setelah refactor, buat atau perbarui test yang relevan.

Minimal test kasus berikut:

### Normal action

```text
Player menyelidiki meja
```

Harus menghasilkan respons investigasi yang valid.

### Invalid modern action

```text
Player membuka smartphone
```

Tidak boleh crash dan tidak boleh otomatis mengurangi HP tanpa alasan.

### Item acquisition

Pastikan item masuk inventory hanya jika game engine memvalidasi event tersebut.

### Item consumption

Pastikan item tidak dapat digunakan dua kali jika hanya tersedia satu.

### Quest completion

Pastikan game tidak selesai hanya karena:

```js
turnCount >= 12
```

### Final scene

Pastikan ending hanya dapat terjadi jika kondisi quest terpenuhi.

### Gemini failure

Simulasikan API failure.

Pastikan deterministic fallback tetap menghasilkan valid scene.

### Invalid Gemini JSON

Pastikan parser/retry/fallback menangani output invalid.

### State consistency

Pastikan:

```text
HP tidak negatif
Mana tidak negatif
Gold tidak negatif jika game rule melarangnya
item tidak muncul secara duplikat tanpa alasan
quest state tidak mundur secara tidak sengaja
```
